# Retained ethanolamine preparation and review packets

This package preserves 22 frozen owners as exact original bytes. It includes author preparations, independent reviews, operational corrections, the accepted graph design, the author authority implementation and the issue 635 host-guard successor. Packaging verifies integrity and portability; it does not grant scientific acceptance, approve maintained implementation or close issues.

All 3,104 physical source files (238,887,425 bytes) are retained in 25 deterministic archives (38,186,035 compressed bytes). The largest archive is 8,200,003 bytes, below the 40 MiB limit. Every archive was exhaustively decoded and reproduced byte-identically in a second stream. Hidden and ignored files, failures, source manifests and freeze proofs are included.

`retention.json` is the portable outer-file/member index. It binds each expected source manifest and freeze, every original relative path/hash/size, each archive and decoded tar stream, and each readable report copy. `packet-specifications.json` independently pins the 22 expected releases. Readable files under `reports/` are exact copies with their correspondence checked against the archived originals; they do not replace the complete archives. The independent ontology insertion-order review is retained inside `authority-implementation/ontology-order-review` and has separately readable copies.

All tar members are regular files in sorted order with fixed owner, mode and time; gzip has no filename and mtime zero. Parts contain consecutive segments of one packet, never a mixture of packets. Every original is retained, including failed downloads whose `.pdf` or `.zip` extension does not make the body a valid document. Nested containers are opaque byte-exact payloads; retention does not inspect their interiors or upgrade prior reading scope.

Operational corrections remain paired with their historical originals: the ignored Ruff-cache write correction, the EutT false lint-pass correction, the ontology key-order successor and the issue 635 rejection-host successor. The native magnesium/citation correction and EutT scientific supplement also retain their independent qualified reviews. Original claims and failed attempts remain unchanged; later successors specify which interpretations are superseded. Issue 634 and issue 635 closure require actual merged-record verification outside this package.

The actual baseline rebind concerns PR 633 merge `54e768a985d07705ea25445804c83b4758646e37`, tree `d2c58cc6e8c7a7650bdf8d4a91f69b2a54ff8bdb`. Earlier discovery and preflight pending-baseline statements remain historical. Active authority review, record preparation and root integration/history are excluded. No global novelty, pathway/source exhaustion, physiological flux, automatic identifier equivalence or public-release licensing claim is made.

Portable verification requires only this directory and an existing Python 3 runtime:

```sh
PYTHONDONTWRITEBYTECODE=1 PYTHONNOUSERSITE=1 python3 -B retain.py verify --output .
PYTHONDONTWRITEBYTECODE=1 PYTHONNOUSERSITE=1 python3 -B check_archived_manifests.py .
```

Both commands are read-only. The first verifies expected packet scope, archive hashes and metadata, every member, complete coverage and readable-copy correspondence. The second independently decodes each archived source manifest/freeze and checks its declared files against the portable member index. Neither verification command requires the original scratch owners, network, Git or database caches. Historical absolute provenance paths inside originals are retained verbatim and are not verifier inputs.

A fresh archive/index/report rebuild can use `retain.py build --sources-root ROOT --output FRESH` with all frozen owners present beneath ROOT; overwrite is rejected. Maintained verification helpers pass the repository's explicit Ruff configuration with `--no-cache`. The historical setup helper is preserved as `.py.txt`, so its original long-line style diagnostics cannot become an active repository Python lint failure. Build and portable replay receipts are retained under `verification/`.
